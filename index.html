02

The problem is bigger than lending

Private capital markets run on the same four manual bottlenecks, fund after fund, regardless of Islamic or conventional structure. A platform that only automates loan origination misses most of the actual pain.

four entry points, one pipeline — problem (left) → solution (right)
1

Onboarding buried in bespoke PDFs

Every GP uses a different subscription document template — 50 to 100 pages, hand-filled, manually checked for AML status and accreditation. One typo costs weeks. This is the same document-extraction problem the platform already solves for loan documents — it just needs to run on subscription docs too, with the same confidence-gated review before anything is accepted as verified.

2

Capital calls with no shared calendar

LPs holding stakes across dozens of funds get hit with capital-call notices in different formats, on no unified timeline, routed through internal approval chains by hand before a wire goes out. There's no centralized payment rail on either side. This is a workflow-orchestration and notification problem as much as an extraction one — parse the notice, normalize it against a due-date calendar, route it through approval, trigger payment.

3

Cap tables that live in spreadsheets

Secondary transfers require manually checking a company's bylaws, routing Board approval or Right-of-First-Refusal waivers, then a lawyer hand-updates a spreadsheet to log new ownership. Trades fall apart or take a month to clear. This is exactly what the tokenization roadmap already targets — an on-chain cap table with transfer rules and approval gates encoded once, not re-derived by a lawyer every time.

4

Portfolio reporting stuck in Excel

Quarterly updates arrive as differently-formatted spreadsheets from every portfolio company; analysts copy, paste, and reconcile by hand, because best-of-breed point tools rarely talk to each other over an API. Same extraction pipeline, aimed at a different document type, feeding the same unified data warehouse instead of a dozen disconnected ones.

The pattern across all four: one AI extraction layer, one compliance gateway, one ledger — applied to every document type and workflow a fund actually deals with, not just loan origination. That's the platform this architecture should be, and the dual-track design already accommodates it.

03

How I'd architect it

Three decisions matter more than any single tool choice. Get these right and the stack underneath is largely a build-vs-buy exercise.

A

Compliance as configuration, not a fork

Every product carries a compliance_mode flag — TRADITIONAL or ISLAMIC. One schema, one audit trail, branching business logic. This avoids the trap most dual-track platforms fall into: maintaining two codebases that quietly drift apart.

B

Confidence-gated extraction, human-in-the-loop by design

Every document extraction — loan terms, profit-share ratios, fatwa references — gets a confidence score. Below threshold, it doesn't guess; it routes to a human reviewer, and for Islamic-track products, to Shariah board review specifically.

threshold: 0.85 for financial extraction — higher than general-purpose RAG, because being wrong here has a different cost
C

Tokenization as a roadmap, not a launch requirement

Real-world asset tokenization is where this platform is headed, not where it starts. Permissioned ledger, identity-gated token standard, Shariah verification module attached at the token level — sequenced after the lending and compliance core is proven with real customers, not before.
